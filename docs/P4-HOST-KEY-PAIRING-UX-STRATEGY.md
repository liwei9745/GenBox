# P4 SSH 主机身份配对体验策略

**日期：** 2026-07-23
**证据范围：** 本文的产品研究为公开文档研究；实现和测试证据只允许标记为 `LOCAL`。本轮不执行真实 SSH 配对、VPS、远程容器或网络部署；浏览器检查只允许使用本地运行时。

## 1. 目标和边界

配对的唯一任务是确认“这个已保存的目标，确实返回了用户在可信 SSH 会话中看到的同一台服务器主机身份”。它不登录服务器、不验证 SSH 密码、不执行部署命令，也不证明 VPS 所有权。完成后只保存后端重新探测并校验过的主机密钥算法和 `SHA256:` 指纹。

本轮服务对象是第一次接触 SSH 的个人用户，同时保留手动核对作为无法使用可信终端时的安全后备路径。配对材料（挑战、命令、响应、指纹候选）只存在于短时请求和页面内存中，不进入浏览器存储、任务记录、日志、截图、URL 或 Git。

## 2. 公开成熟做法研究

以下结论来自 2026-07-23 对公开文档的阅读，来源均为 `VERIFIED` 的文档内容；它们不是 GenBox 的运行证据。

| 来源 | 观察到的做法 | 适用于 GenBox | 风险与取舍 |
| --- | --- | --- | --- |
| [GitHub SSH key fingerprints](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/githubs-ssh-key-fingerprints) | 发布可独立核对的公开主机指纹，并给出 `known_hosts` 记录；指纹是连接身份而不是用户凭据。 | 在 UI 中同时保留算法和完整 SHA-256 指纹，要求服务商控制台或既有可信记录带外核对。 | 只显示截断指纹会增加误判；把指纹当密码或放入普通日志会扩大泄露面。 |
| [GitHub host-key error guidance](https://docs.github.com/en/authentication/troubleshooting-ssh/error-host-key-verification-failed) | 已知主机键变化时明确阻断，要求先从可信来源确认变更，而不是直接删除检查。 | “已变更/不一致”进入失败态，给出“重新读取、重新开始、检查可信来源”的恢复路径；不提供绕过检查的按钮。 | 重建服务器导致合法变更，用户需要可理解的恢复提示；自动接受会掩盖中间人风险。 |

| [DigitalOcean OpenSSH guide](https://docs.digitalocean.com/products/droplets/how-to/connect-with-ssh/openssh/) | 通过控制台给出可复制的 `ssh user@host` 形式命令，解释第一次连接和 `known_hosts`；故障时给出明确的下一条诊断动作。 | 使用单条、后端生成、不可由浏览器编辑的 helper；复制后只粘贴最后一行回页面，错误时可重新生成。 | “复制即运行”容易让用户把命令粘到错误主机；页面必须写明“只在已信任的 SSH 窗口运行这一行”。 |

## 3. 设计策略

### 3.1 单一主任务和步骤状态

面板标题固定为“在已登录的 SSH 终端里确认服务器”，上方只保留两个编号步骤：

1. **复制命令并在可信终端运行**：开始请求加载时禁用开始按钮；成功后显示只读命令和复制按钮，并把焦点放在复制按钮。
2. **粘贴结果并提交**：只接受以 `GENBOX-PAIR/1` 开头的固定格式响应；有内容后启用“提交验证结果”，提交期间禁用输入和按钮。

步骤状态通过 `active`、`completed` 和错误/过期提示表达，不能只靠颜色；窄屏改为纵向堆叠，按钮保持可触控宽度。复制失败时保留文本选中能力并给出手动复制提示。

### 3.2 生命周期和恢复

- **空闲：** 显示开始按钮和“不会保存密码/私钥/配对响应”。
- **加载：** 显示正在生成一次性命令，阻止重复请求。
- **等待粘贴：** 显示命令、短时有效提示和输入框；页面内存记录过期计时器。
- **成功：** 清空命令、响应和计时器，只显示“服务器身份已验证”，随后引导输入 SSH 凭据。
- **失败：** 后端错误映射为安全、可行动的中文提示；不回显原始响应、指纹或异常堆栈。可重新开始，不能在失败后复用挑战。
- **过期/取消：** 清空所有临时字段，保留已保存目标但不保存任何身份，主按钮恢复为“重新开始/生成验证命令”。
- **目标被编辑或切换：** 立即使旧请求和旧配对失效，隐藏配对面板，要求对新身份重新开始。

后端继续执行主机密钥算法白名单、完整 `SHA256:` 格式校验、挑战单次消费、目标身份版本绑定、完成前重新探测和 compare-and-swap 保存。前端状态不能替代这些检查。

### 3.3 安全文案和数据边界

- 只说“公开主机身份”，不说“已登录”“已拥有 VPS”或“已安全”。
- 明确“不要在这里输入 SSH 密码、私钥、私钥口令或 sudo 密码”；凭据字段继续使用 `autocomplete=off`，不进入配对请求。
- 不显示或持久化原始终端输出；输入框 placeholder 只描述固定协议前缀。
- 错误提示使用通用恢复动作：检查可信终端、确认目标未被重建、重新生成；不泄露 host、IP、用户名、指纹或服务器输出。
- 不提供关闭 host-key 检查或自动接受变更键的控件。

### 3.4 可访问性和窄屏

- 使用真实 `button`、`label`、`textarea`，状态区域带 `role=status` / `aria-live=polite`。
- 步骤列表使用可读文本，不只依赖颜色；按钮在键盘焦点下有明显轮廓，复制后焦点仍在复制按钮。
- 命令和响应文本框允许换行显示、`overflow-wrap:anywhere`，不让长 token 撑破布局；窄屏下命令和按钮纵向排列。
- 提交按钮在输入为空、加载中、离线、过期时均 disabled；Escape/取消通过“重新开始”清空内存状态。

## 4. 本地实现清单

1. 保留当前未提交的分步 UI、复制按钮、可信终端说明和手动核对 fallback。
2. 增加前端短时过期计时器和明确的过期状态，过期自动清理临时材料并允许重新开始。
3. 对复制成功、复制失败、提交加载、后端拒绝、目标切换分别覆盖 focused tests。
4. 用 Node 语法检查、配对后端 pytest、静态 UI 测试和完整本地测试验证；浏览器只访问 `http://127.0.0.1:8892/#/extensions`，证据标记为 `LOCAL`。

## 5. 剩余风险与阻塞

- 可信 SSH 会话仍是用户提供的初始信任锚点，不能证明 VPS 归属；没有可信会话的用户必须走服务商控制台/既有 known-host/手动核对。
- 本轮不验证真实 SSH、VPS 隔离、远程容器、私网链路或生产非变更；这些仍是 L2 及后续门槛。
- 浏览器剪贴板权限可能被拒绝，因此必须保留手动选择复制的恢复路径。
