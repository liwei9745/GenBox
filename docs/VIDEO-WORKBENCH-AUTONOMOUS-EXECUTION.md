# Video Workbench 无人值守执行协议

日期：2026-09-18（UTC）。修订：0.4。
状态：**WB-1 启用；W1-2 依赖诊断、素材分页与存储故障子门已本地验证。**

本协议把“无人值守”定义为：在当前已授权的隔离工作树内，协调者可以
连续完成低风险的读取、实现、测试、证据整理和本地提交；只有命中明确的
安全、契约、费用、数据损失或外部发布门槛时才暂停并请求人工确认。

它不是后台守护进程，也不代表 Codex 会在会话结束后继续运行。每次会话
结束前必须留下可恢复的状态；下一次会话从状态、Git 和测试证据重新核对，
不能仅凭聊天记录继续。

## 1. 适用范围和优先级

适用范围：

- 分支：`codex/wb1-baseline-20260918` 及其后续专用 `codex/` 分支。
- 阶段：WB-1 的 W1-2/W1-3/W1-4；当前先启动 W1-2。
- 环境：本地 GenBox 和隔离开发工作树。
- 素材：`tests/fixtures/video_workbench/` 中的合成夹具及测试临时目录。

规则优先级：

1. `AGENTS.md` 和现有安全/生命周期约束。
2. `docs/VIDEO-WORKBENCH-CONTRACT.md` 及其冻结修订。
3. `docs/VIDEO-WORKBENCH-WB1-FIXTURES.md`、本协议和实施计划。
4. 当前任务包和测试证据。

下层任务、Agent 提示或模型输出不得放宽上层约束。发现冲突时暂停，
记录冲突，不自行猜测。

## 2. 默认自动执行清单

以下操作可以在隔离工作树内自动完成，不需要逐步询问：

- 读取仓库文件、CodeGraph（如存在）、测试和静态分析结果。
- 生成、校验和重新计算合成夹具的大小及 SHA-256。
- 在冻结 DTO、错误码、资源限制和所有权矩阵内实现代码。
- 运行单元、路由、契约、浏览器和现有回归测试。
- 对可定位的低风险测试失败自动修复，最多连续两轮。
- 运行 `py_compile`、`node --check`、`git diff --check` 和格式检查。
- 在已声明的 owned paths 内创建目录和临时文件。
- 生成脱敏的阶段报告、任务交接记录和 `STATUS.md` 恢复信息。
- 创建只包含当前任务文件的本地提交。
- 推送专用开发分支；推送前自动执行秘密/个人数据扫描。
- 失败后自动回到 `blocked`，保留现场，不进行清理式重试。

自动执行不包括“自动批准”。任何测试通过只能改变证据状态，不能改变
契约、Phase 完成状态或发布状态。

## 3. 必须人工确认的门槛

命中任一项，立即暂停，不执行后续副作用：

- 访问、重启、修改或部署生产实例、VPS、Docker 远程服务或真实用户环境。
- 使用真实 Provider、API Key、付费额度、真实 Omni/Veo 编辑请求或网络上传。
- 上传私人素材、真实账户数据、用户提示词或未脱敏日志。
- 删除、覆盖、迁移、清理或改变任何用户源媒体、运行数据或持久化密钥。
- 修改冻结契约、DTO、错误码、资源限制、存储布局、认证/CSRF/所有权边界。
- 修改共享入口（例如 `main.py`、`static/index.html`、全局 CSS、既有任务存储
  或既有 Provider 协议）而任务包没有明确授权。
- 新增依赖、改变许可证边界、引入新的编解码器或作出打包支持承诺。
- 合并 PR、创建/移动 Tag、发布 Release、构建并发布镜像或触发工作流。
- 需要修改其他 Agent 的 owned paths，或需要合并存在冲突的分支。
- 任何可能造成费用、重复提交、数据丢失、权限扩大或安全边界下降的操作。

人工确认必须说明：目标、预计副作用、最小范围、备份/回滚、验证命令、
是否会产生费用，以及拒绝后的安全状态。

## 4. 自动暂停条件

出现下列任一情况，任务状态改为 `blocked` 或 `needs_revision`，并写入
恢复记录：

- 测试失败无法在当前轮次定位，或同一问题连续两轮修复仍失败。
- 实际行为要求新增字段、扩大限制或偏离冻结契约。
- 路径、所有权、分支基线、运行时身份或目标环境不明确。
- 发现秘密、个人数据、私人素材、绝对路径或未脱敏日志可能进入 Git/报告。
- FFmpeg/ffprobe 缺失、行为跨平台不一致，或无法证明资源边界。
- 需要网络、凭据、真实媒体、外部服务或人工视觉判断。
- 检测到重复任务、重复提交、锁失效、源文件变化或无法安全回滚。
- 依赖的接口/任务包尚未满足，或与 `origin/master`/冻结文档产生冲突。

暂停不是失败结论。必须保留最后一个安全状态，不删除现场，不用盲目重试
掩盖问题。

## 5. 任务生命周期和无人值守循环

每个任务只能按下列状态推进：

`planned -> ready -> running -> review -> integrated -> accepted`

也可转为 `blocked` 或 `needs_revision`。协调者每一轮自动循环执行：

1. 读取 `STATUS.md`、实施计划、任务包和当前 Git 状态。
2. 校验分支、基线、owned paths 和冻结夹具摘要。
3. 只实现一个可验证的小切片。
4. 运行该切片的 focused tests，再运行必要的共享回归。
5. 检查差异、秘密、路径边界和契约偏差。
6. 记录命令、结果、运行时身份、未验证事项和下一步。
7. 通过后创建本地提交；未通过则按第 4 节暂停或进入下一轮修复。

连续两轮修复后仍不通过，必须回到任务拆分或契约审查，不能自动放宽
验收条件。`accepted` 只能由独立检查或协调者基于实际证据确认。

## 6. Git、分支和文件边界

- 不使用 `reset --hard`、`checkout --` 或递归删除来清理现场。
- 不触碰用户已有未跟踪文件；临时文件必须位于任务专属目录。
- 提交使用明确文件列表，不使用宽泛的 `git add .`。
- 协调者拥有权威文档、共享入口、发布文件和最终集成提交。
- Worker 只修改任务包声明的 owned paths；共享文件变更必须暂停交接。
- 推送只允许专用开发分支；主分支、Tag、Release 和镜像发布均需人工确认。

## 7. 证据和恢复记录

每次阶段结束或暂停都必须记录：

- 日期时间、阶段/任务 ID、分支和 commit。
- 本轮目标、已修改文件和未修改的共享文件。
- 使用的夹具及其 manifest/digest 校验结果。
- 完整测试命令、通过/失败结果和运行时身份。
- 契约偏差、未验证行为、风险和阻塞原因。
- 是否触及网络、凭据、真实媒体、费用或外部副作用。
- 恢复后的第一条安全命令。

恢复时按顺序执行：读取记录 -> `git status`/`git log` -> 重跑最小失败
测试 -> 检查是否仍满足人工门槛 -> 再继续。不得从旧聊天摘要直接推断
“已完成”。
