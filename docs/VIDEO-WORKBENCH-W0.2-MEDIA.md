# Video Workbench W0.2 Media Feasibility

Date: 2026-09-18. Revision: 0.1.
Stage: G1 media feasibility.
Status: Evidence collected; numeric limits and packaging decisions remain
`PROPOSED` pending W0.5 review.

This report is a bounded local media spike for the independent video workbench.
It does not implement an importer, project store, proxy service or render job
route. It does not certify any desktop/container distribution, cloud provider,
user media, or future online editing model.

## Scope And Safety

The spike used only synthetic media generated with FFmpeg `lavfi`
`testsrc2`/`sine` sources. No private footage, user prompt, credential,
network download, paid generation request or remote upload was used. Temporary
artifacts are under:

```text
.pytest-tmp-workbench-media/w02-20260918/
```

The local machine is a Windows 10 Pro build 19045 host with an Intel Core
i5-13400 (10 physical / 16 logical processors) and 15.62 GiB visible RAM.
These host facts are dated local evidence, not a product minimum.

## Proxy And Render Spike

`VERIFIED / LOCAL / 2026-09-18`: the local engine created a 320x180 H.264
proxy from `cfr-h264.mp4`, a one-second silent trimmed render, and a 1.5-second
trimmed A/V render:

```powershell
ffmpeg -i cfr-h264.mp4 -vf scale=320:180:flags=bicubic -an `
  -c:v libx264 -preset ultrafast -crf 30 -pix_fmt yuv420p `
  -movflags +faststart proxy-h264-320x180.mp4

ffmpeg -ss 0.5 -t 1.0 -i cfr-h264.mp4 `
  -vf scale=320:180:flags=bicubic -an -c:v libx264 `
  -pix_fmt yuv420p -movflags +faststart render-trim.mp4

ffmpeg -ss 0.25 -t 1.5 -i av-aac.mp4 `
  -vf scale=320:180:flags=bicubic -c:v libx264 -c:a aac -b:a 128k `
  -pix_fmt yuv420p -shortest -movflags +faststart render-av-trim.mp4
```

On this host, one warm local run measured approximately:

| Operation | Elapsed |
| --- | ---: |
| Probe a fixture with `ffprobe -show_entries` | 53-62 ms |
| Decode a fixture to null output | 54-81 ms |
| Create 320x180 H.264 proxy from 2 s synthetic video | 103 ms |
| Render 1.0 s silent H.264 trim | 119 ms |
| Render 1.5 s H.264/AAC trim | 124 ms |

These are tiny synthetic files and are not a real-time or hardware-neutral
benchmark. They establish that an isolated worker can execute the basic
operations, not that a browser timeline should invoke FFmpeg synchronously.

The resulting `render-av-trim.mp4` had a 1.500 s container/audio duration and a
1.480 s video-stream duration. That small stream-boundary difference is a
useful warning: export validation must inspect per-stream durations and A/V
sync, not only container duration.

## Feasibility Findings

### `VERIFIED`

- FFmpeg/ffprobe can probe and fully decode the synthetic H.264 MP4, VP9 WebM,
  H.264/AAC MP4, VFR MP4, WAV, MP3 and JPEG fixtures.
- The local engine can create a bounded H.264 proxy and render trimmed
  silent/A/V MP4 outputs.
- A VFR input can report a nominal frame rate that differs from its average
  frame rate. The workbench needs rational time bases and explicit source
  timing; it must not accumulate floating-point seconds or assume every input
  is CFR.
- Audio-only WAV and MP3 can be decoded independently, and AAC can survive a
  mixed A/V render.
- A thumbnail can be generated as a separate still asset without changing the
  source file.

### `PROPOSED`

These are candidates for W0.5 ratification, not frozen implementation
requirements:

1. Use an isolated FFmpeg/ffprobe worker boundary with argument arrays and
   bounded wall time, memory, process count and output size. Never pass browser
   strings as shell commands.
2. Store source time values as integer microseconds and retain each stream's
   rational time base. Normalize VFR/rotation/sample-aspect/PTS in a
   controlled preparation step before timeline editing.
3. Initial import matrix:
   - video: MP4/H.264 + AAC or no audio; WebM/VP9 as an explicitly supported
     secondary input if packaged-runtime tests pass;
   - audio: WAV/PCM and MP3; AAC only when carried by an accepted container;
   - stills: PNG/JPEG/WebP after actual decoder validation;
   - output: MP4/H.264 `yuv420p` with AAC when audio is present.
4. Preserve original managed bytes and metadata. Generate a separate proxy,
   thumbnail and export; never overwrite the source on trim, transcode or
   preview generation.
5. Reject or quarantine unsupported/ambiguous inputs rather than silently
   transcoding them. Browser MIME and suffix are hints only.
6. Require output validation for decode, duration, dimensions, expected stream
   count and A/V synchronization before atomic publication.
7. Start with a bounded preview envelope of 720p proxy media and a short
   project duration; freeze exact byte/dimension/duration/clip/concurrency
   limits only after a memory/disk benchmark on declared package targets.
8. Keep source, proxy, thumbnail, project, export and candidate lifetimes
   separate. Cleanup must only remove owned reproducible derivatives with no
   active lease.

### `UNVERIFIED`

- Whether the same codec set and FFmpeg build are available in the current
  Windows/macOS/Linux desktop artifacts and Docker image.
- Browser-native playback behavior for every proposed input, especially VP9
  WebM, VFR, rotation metadata and unusual audio sample rates.
- Decoder behavior and resource consumption for large, long, corrupt, malformed
  or adversarial files.
- Exact importer limits, chunking/resume behavior, disk reservation, worker
  cancellation and restart recovery; no workbench importer exists yet.
- Rotation, non-square pixel aspect, edit lists, negative/irregular PTS and
  mixed sample-rate timeline normalization.
- Cross-platform output parity, hardware acceleration, and license/
  redistribution implications of shipping a particular FFmpeg build.
- A/V sync tolerance under repeated cuts, concatenation, resampling and
  longer projects.

## Candidate Matrix And Limits For W0.5

The following table is deliberately marked `PROPOSED`; it must not be read as
an already accepted schema or public product promise.

| Concern | Candidate initial boundary | Why it is needed | Required follow-up |
| --- | --- | --- | --- |
| Video input | MP4/H.264 baseline; WebM/VP9 conditional | Matches verified local fixtures and broad browser support | Package/browser matrix |
| Audio input | WAV/PCM, MP3; AAC in accepted MP4 | Covers independent and mixed tracks | Sample-rate/resampling tests |
| Output | MP4/H.264 `yuv420p`; AAC if audio exists | Predictable playback/export target | Windows/macOS/Linux/container smoke |
| Duration | Start with short projects; exact maximum pending | Bounds probe/render cost | Measure 2-minute/20-clip target |
| Dimensions | Start with 1080p source and 720p proxy target | Keeps preview bounded | Memory and disk benchmark |
| Clips | Start with 20 picture clips and one audio track | Aligns acceptance envelope | Stress test timeline/project JSON |
| Jobs | One bounded local probe/render per worker; exact concurrency pending | Prevents unbounded process fan-out | Cancellation/restart tests |
| A/V sync | Validate per-stream durations; candidate tolerance 50 ms | Prevents silent drift | Ratify on mixed-media fixtures |
| Temp storage | Owned staging/proxy/export dirs, atomic publish | Prevents partial visible assets | Disk-full/orphan recovery tests |

The acceptance document's proposed 2-minute/20-clip/1080p project, 720p proxy,
500 ms warm seek, 100 ms local action feedback, one-frame export tolerance and
50 ms synthetic A/V sync target remain `PROPOSED` until measured on supported
targets. This report does not promote them to `PASS`.

## Blockers And Next Actions

`BLOCKER / W0.5 REQUIRED`: no exact supported codec/container/resource matrix
is frozen yet. The local spike is sufficient to choose FFmpeg as the first
engine candidate, but not sufficient to authorize WB-1 implementation or
release packaging.

Before WB-1, the coordinator/reviewer should:

1. Ratify or revise the proposed input/output matrix and numeric limits.
2. Run the fixture matrix on each declared desktop/container target.
3. Add VFR, rotation, corrupt, no-audio, oversized and disk-full fixtures.
4. Define the importer worker, cleanup, cancellation and restart evidence.
5. Measure the 2-minute/20-clip performance envelope and record memory/disk.
6. Define whether VP9/WebM is input-only, exportable, or conditional.
7. Review FFmpeg build/licensing/redistribution implications for each artifact.

Until those actions are complete, W0.2 should be treated as evidence-backed
feasibility with an open contract decision, not as an implementation-ready
media specification.
